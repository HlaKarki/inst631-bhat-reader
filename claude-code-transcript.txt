❯ alright first of all, i need to be able to get the bounding boxes of the
  highlighted areas. did we already have those in the data.json?
⏺ Yes. Every note in data.json has a rects array, and those rects are the
  highlight boxes.

  What the rects are

  Each rect is one highlighted line, not the whole passage. A note that spans 5
  lines has 5 rects. Note 1, for example, is the abstract highlight on page 1:

  "rects": [[0.428, 0.4591, 0.0524, 0.0113],
            [0.0879, 0.4728, 0.3925, 0.0114], ...]

  Each rect is [x, y, w, h] as a fraction of the page. x and y are the top-left
  corner, measured from the page's top-left, and w and h are the width and
  height. So 0.428 means 42.8% of the way across the page. To get pixels,
  multiply by the rendered page size: x * imgWidth, y * imgHeight. That's why
  the starter sets left: x * 100% and the like. The numbers stay correct at any
  zoom.

  If you need one box per note

  The data has no single box per note. You get it from the union of the line
  rects: the smallest x and y, and the largest x + w and y + h. One catch: a
  highlight that runs from the bottom of one column to the top of the next gives
  a union box covering both columns. The box then includes unhighlighted text
  in between. For hover targets and scroll-to, the per-line rects are more
  accurate. The union box is good for a card's anchor point or its vertical
  position.

  I can also add a precomputed bbox field per note in build_part3.py if you'd
  rather not compute it in the app.

  - Decide how shared highlights should behave. Two pairs of notes cover exactly
    the same lines, so one note in each pair can't be hovered. Options are

  Hover works

  Hovering any line of a note now lights every line of that note: opacity goes
  from 0.34 to 0.62, with a 0.15s fade. Moving the pointer off returns it to
  normal.

  A headless check hovered note 2 and got 4 lit rects. After the pointer left,
  it got 0. Vite already hot-reloaded your dev server on 5174. The build passes.
  I haven't committed this yet, because your answer below might change the
  code.

  The change in src/main.ts: the rect loop now collects a note's highlight
  elements into hls. Each one gets pointerenter and pointerleave listeners that
  toggle a lit class on the whole group. src/style.css adds the transition and
  the .hl.lit rule.

  The overlap

  Notes 1 and 3 on page 1 have identical rects: note 1 is the central idea and
  note 3 a definition, both on the abstract's "We posit self-awareness..."
  sentences. Notes 18 and 19 on page 4 also match exactly: method and your own
  question, both on the recruitment sentence.

  build_part3.py stretches each highlight to full sentences, so two notes
  anchored in the same sentence end up with the same boxes. The later note's
  divs sit on top, so notes 3 and 19 catch every hover, and notes 1 and 18 are
  unreachable. The two colors also stack, which is why note 1 looked orange
  instead of red.

  There are two ways to handle it:
  - Light the passage, not the note. Hovering a shared passage lights every note
    anchored there. This fits once note cards exist, where hovering could
    highlight both cards.
  - Give each note its own handle. Leave hover as it is and add the numbered
    margin markers from the old reader. Each note gets a marker you can always
    hover, even when its highlight is covered. Hovering the marker lights the
    note.

  I'd do the second one. It's what the old reader did, and markers are probably
  the next thing you'd build anyway.

  only, with no Prettier, no oxfmt and no editorconfig.

  What's there

  Oxlint runs with bun run lint. .oxlintrc.json turns on the react, typescript
  and oxc plugins, plus two React rules: rules-of-hooks as an error, and
  only-export-components as a warning, so fast refresh keeps working. It
  currently reports nothing.

  Formatter options

  - Prettier (3.9.9). Stable and the default in most editors, so format-on-save
    just works. It's the safe pick.
  - oxfmt (0.71.0). From the same team as oxlint and much faster, but still
    pre-1.0, so expect occasional changes in output. For a repo this small, the
    speed doesn't matter.

  I'd go with Prettier. Whichever you pick, it needs a small config to match the
  current code, which has no semicolons, uses single quotes, and runs lines to
  about 120 characters. Without that config, the first format run rewrites every
  file. I'd add a format script next to lint too.

⏺ WebStorm doesn't use oxfmt on its own. Its "Reformat Code" runs WebStorm's
  built-in formatter, which knows nothing about .oxfmtrc.json. That means your
  selection was formatted by WebStorm's own rules, or left alone.

  Fix

  1. Install the Oxc plugin from the JetBrains Marketplace (Settings → Plugins →
     search "Oxc"). The oxc team makes it. It runs oxfmt --lsp from the
     project's own node_modules, which the reader app now has.
  2. Turn on oxfmt formatting in the plugin's settings. The README lists format
     on save, and hooking into Code → Reformat Code / Reformat File. I haven't
     checked the exact settings path. It should appear under the plugin's
     settings page once installed.

  Selection formatting

  Formatting a selection may still not work. The plugin docs don't say whether
  they support range formatting. The oxfmt CLI has no range option either. It
  always formats whole files. So use "Reformat File" or format on save, not
  "Reformat selection". The terminal fallback always works: bun run format.

  Sources:
  - Oxc formatter editor setup
  - Oxc plugin on JetBrains Marketplace
  - oxc-intellij-plugin README

⏺ cn is in. The faster one you were thinking of is shadcn's new cn package, made
  by shadcn and Aiden Bai. It replaces clsx plus tailwind-merge in one package
  with the same API. The README claims it's about 30× faster, with output
  identical to tailwind-merge. It's v0.4.0, published 9/22, so it's new and
  still pre-1.0.

  Setup

  src/lib/utils.ts is one line, export { cn } from 'cn', so imports read import
  { cn } from '@/lib/utils' like your other projects. If cn ever causes trouble,
  that file is the only place to swap it back to twMerge(clsx(...)).

  oxfmt now also sorts the classes inside cn(...) calls (functions: ["cn"] in
  .oxfmtrc.json), not just className strings.

  Where it's used

  Classes are grouped one concern per string, the same way as your Portfolio's
  buttonBrandVariant:

  className={cn(

    'bg-(--c)',
    'transition-opacity duration-150',
    lit ? 'opacity-62' : 'opacity-34',
  )}

  Sheet uses cn('relative w-full max-w-[816px]', 'shadow-[...]'). Home's <main>
  is all layout, so it stays a plain string.

  Build, lint and format are clean, and the hover check still passes. I skipped
  the package's optional cn build Vite plugin, which trims the bundle further.
  At this app's size, the 26 KB default doesn't matter.

❯ alright on the mobile, how do i tackle the problem of the paper being small?

⏺ The best fix is to show one column of the paper at a time on phones. Each page
  gets split into its left and right columns, and each column is stacked at
  full screen width. That makes the text about 2.3× bigger without
  pinch-zooming, and reading still runs top to bottom.

  Why it's small

  The paper is a two-column page 816 px wide. A phone gives it about 358 px, so
  everything shrinks to 44%, and body text ends up around 5 px. You can't fix
  that by scaling the whole page, because a full page never fits a phone width
  at a readable size. A single column is 39% of the page width, so it can fill
  the screen at about 12 px text.

  Options

  - Column reflow (recommended). On phones, render each page as strips: page 1's
    title and author block as one full-width strip, then the left column, then
    the right column. Rects map cleanly because they're already page fractions.
    A rect in the left column is just re-scaled to that column's box, so
    highlights, hover, spotlight and the bottom sheet all keep working. This is
    how most phone PDF readers handle two-column papers.
  - Zoom to the passage on tap. When a note opens, scale the page so its passage
    fills the width above the bottom sheet. This helps read what you tapped,
    but the rest of the paper stays tiny. It could be added on top of reflow
    later.
  - Pinch-zoom only. It's free, since the browser already allows it. But fixed
    elements like the bottom sheet act strangely while zoomed, and you're
    panning around constantly. It works as a fallback, not a design.
  - Real text reflow. Extract the paper's text and render it as HTML. It's the
    most readable, but you lose the paper's look, and every highlight would need
    re-anchoring to text offsets. The assignment asks for the manuscript
    itself, so I'd skip this.
